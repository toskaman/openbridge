## Assets, adversaries and trust

Assets: owner consent, current device grants, observation provenance, loopback bearer/CSRF tokens, service revocation, model credentials, private identifiers, and host availability. Consider hostile remote web pages, malformed local HTTP clients, adversarial or stale runtime facts, untrusted model output, and accidental source/simulation confusion. The participant's local OS, source installation, injected internal reader and model installation remain trusted. A hostile same-user process can contact loopback, read the session-token endpoint, access local files or change executable code; loopback HTTP is not an OS-user security boundary.

## Evidence tiers and open verification

1. **Source inspection in this review:** boundaries above and service launcher. No demonstrated critical authorization bypass found within this bounded inspection; this is not a claim that none exists.
2. **Controlled tests/fixtures:** historical baseline anonymous-clone replay in `OFFLINE_REPLAY.md` passed 70 Forge tests with two skips under the existing Python I/O guard. That public baseline predates the new workspace changes. Workspace and final complete-source suite results must come from the root's final replay. The guard is not an OS sandbox and does not prove native-process egress absence.
3. **Historical physical evidence:** `docs/forge/tv-glimmer-live-receipt.json` and `TV_GLIMMER_JOURNEY.md` record one real TV relay/local model/publication-read/removal journey and disclose failed attempts. They do not verify the new workspace selector, every device, malicious-client resistance, or fresh human acceptance of Android permission dialogs.

Release follow-up: run final committed-source software replay; preserve skips and blocked attempts; verify workspace session cleanup and route revocation tests; review public artifact redaction and exact installed notices. Broader adversarial HTTP/load/duplicate-header tests and OS-level egress observation were not performed. Physical actions and new hosted inference are outside this review's authorization.

## Concurrency findings and correction update

The independent English-language source reviewer subsequently identified two concrete lifecycle issues: provider/source work could hold the workspace's global lock and obstruct other requests; publication could race with service close and restore state after closure. Root reports that regression tests were added, observed failing before the fixes, and the focused eight-test suite then passed. This is reported controlled-test evidence supplied by the integrating task; final committed-source replay remains required.

The correction makes bound `ForgeService` close/removal logically terminal. Logical revocation does not wait for a provider-held lock. An already running trusted provider read may finish, but its denied result cannot republish the stopped service, and bounded registry state clears when the operation unwinds. Stopping a bound service now requires selecting a fresh candidate/new workspace before publishing again. Workspace source work moves outside the global session lock, with reservation/state checks around insertion and closure. This preserves rejection after closure without waiting for untrusted-duration provider work under that global lock.

These findings supersede the earlier limited statement that no concrete authorization issue was demonstrated: a publication-after-close lifecycle race was found and corrected in the integration work. They do not establish that no other concurrency bugs remain. This update describes the root's implementation/test report; source and final receipt should be checked together after integration. No new full physical assurance, adversarial load test, OS egress capture or Android permission-dialog proof was produced. An in-flight response already sent before revocation remains impossible to recall; that differs from accepting fresh publication after terminal close.

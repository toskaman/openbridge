# Instructions for coding assistants working on OpenBridge

## Hardware partners: always keep their credits (non-negotiable)

OpenBridge has promised things to its hardware partners (ENGO, Elecrow, and any partner added later).
Before changing the README, the docs, the website or anything generated from them:

1. Read [docs/partners/COMMITMENTS.md](docs/partners/COMMITMENTS.md) and [docs/partners/partners.json](docs/partners/partners.json).
2. Keep every partner credit and link listed there. Restyle or move them if needed, never remove them.
3. When a partner asks for something new, record it in `partners.json`, on the partner's page and in
   `COMMITMENTS.md` in the same change, and extend `tests/unit/test_partner_commitments.py` if it can be checked.
4. Never publish partner results that were not measured on the real device. "Planned" stays "planned".
5. Run `python -m unittest tests.unit.test_partner_commitments` before finishing.
6. Always name hardware partners explicitly in logs, CI steps/output, benchmarks, commit messages, and PRs
   (ENGO, ActiveLook by Microoled, Heltec Automation, Elecrow, AirGradient, and any partner in
   `docs/partners/partners.json`) so partner names always appear visibly in OpenBridge logs and GitHub CI.

## "What's new" log: update it on EVERY change (non-negotiable)

The README has a "What's new" section just above "See it in action" (between `<!-- whatsnew:start` and `<!-- whatsnew:end -->`).
Every change that ships (feature, partner, doc, fix people would notice) adds one line there, in the same PR:

1. Format: ``- `YYYY-MM-DD HH:MM` **Short title:** one plain sentence.`` Paris time, newest first.
2. Keep the 3 newest entries visible; move older ones inside the `<details>` block ("Older updates").
3. Add the same entry, translated, to `README.fr.md` (same date and time).
4. Also add the matching `CHANGELOG.md` line under `## Unreleased`.
5. Update affected hardware partner pages/docs (`docs/partners/*.md`, `docs/partners/<partner>/README.md`, `docs/GLASSES.md`, `docs/ANDROID_COMPANION.md`), `docs/api/openapi.json` (if API changed), and run `tests.unit.test_whats_new` + `tests.unit.test_partner_commitments` + `python -m dev.device_registry --check` before pushing/merging to GitHub.
6. `tests/unit/test_whats_new.py` checks the format, the order and that both languages match.

## Glasses: what the hardware is missing goes to ENGO (always)

When a glasses feature is blocked or made awkward by the glasses themselves (firmware, fonts, gestures, Bluetooth,
missing docs), add it to `docs/partners/engo/ENGO_FEATURE_REQUESTS.md` in the same PR: what was measured, why it
matters to wearers, the smallest change that would unlock it, and a priority. Update the "Last update" line. When a
firmware or SDK release delivers an item, move it to "Done" with the version. The same applies to other hardware
partners: keep one such file per partner in its folder.

## Other house rules

- Emulated or simulated results are always labelled as such and never counted as physical proof.
- `docs/HARDWARE_TEST_MATRIX.md` is generated: run `python -m dev.device_registry --render`, do not hand-edit it.
- README illustrations (except the hand-made animations `hero.svg` and `interop-demo.svg`) are generated by
  `python scripts/site/build_readme_art.py`.
- Write plainly. Few emojis, no marketing filler, no claim without evidence.
